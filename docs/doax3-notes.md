# DOAX3 Fortune (PS4) notes

Dead or Alive Xtreme 3 Fortune, CUSA04555, base 1.00. Asked for by the user on 2026-11-17. Since 2026-11-17 the viewer shows each costume at rest with the face and a hairstyle (`--doax3`, the DOAX3 button), with colour textures since 2026-11-18; this file holds what was read from the files. Nothing is compared with the running game (the port in `/home/pandi/Ports/Apps/DeadOrAliveXtreme3Fortune-Doax3FortunePc` needs update 1.19 and three PS4 system modules the user does not have).

## Getting the files out of the PKG

The game data is `game/base-clean/uroot` in the port's folder, extracted on 2026-11-17. LibOrbisPkg's PkgTool v0.2 is the only PKG tool at hand and runs only on .NET 10 here (`DOTNET_ROLL_FORWARD=Major`, `~/Ports/Runtimes`). On .NET 6 and later its reads come back short and it leaves zeros: the tail of every compressed 64 KiB block in `pkg_extract`, and about 2.1 GB of holes when it reads `pfs_image.dat` out of the outer image (`pkg_extractinnerpfs`). Its `pkg_validate` reports "PFS Image Digest" invalid and the PKG has 22 MiB of zeros at 0x3700000, but read the way below every one of the 288022 inner blocks unpacks, so that damage, if it is any, falls outside the data.

1. `PkgTool pkg_extractouterpfs --passcode 00000000000000000000000000000000 GAME.pkg outer.pfs`: only decrypts (without the passcode it fails with "key is not a valid size").
2. `tools/re/ps4_pfs.py extract outer.pfs outer_files uroot/pfs_image.dat`: the outer image has signed inodes (36-byte block pointers) and the file needs double indirection.
3. `tools/re/ps4_pfsc.py outer_files/uroot/pfs_image.dat inner.pfs --bad bad.txt`: PFSC, 64 KiB blocks, zlib with the small-window header `48 89`, or raw when stored at full size.
4. `tools/re/ps4_pfs.py extract inner.pfs base-clean 'uroot/*'`: 3317 files, all stored contiguously.
5. `sce_sys/param.sfo` lives in the PKG's header entries, not in the PFS: `PkgTool pkg_extractentry GAME.pkg 11 param.sfo`.

## Archives

`uroot/00/Archive.psarc` (2144 files, 0.9 GB) and `uroot/01/Archive.psarc` (4140 files, 14.8 GB): plain PSARC 1.4, zlib, 64 KiB blocks, with the manifest as entry 0 (`tools/re/psarc.py list|extract`). Loose files sit beside them under `00/` and `01/` (`.ywrk`, `.phyd`, `.sktm`, `.misc` and a few models). `tools/re/psarc_repair.py` rebuilds a lost table of contents from the block table; it was written while the extraction was still broken and is not needed with the files above.

Characters, three-letter codes: AYA, HEL, HON, HTM, KAS, KOK, MAR, MOM, NYO (archive 01, 460 files each: 230 costumes as `TMC` and `TMCL`, every outfit fitted to each body, such as `KOK_KAS_CM_00_B`). Archive 00, per character: `face/face_00`, `hair/hair_00` to `hair_05`, one costume (`KAS_fr_00_a`), `animation/*_INGAME_MPM.mpm`, `*_FACE_MPM.mpm`, `*_DAT.bin`; loose: `animation/*_INGAME_SKTM.sktm`, `*_FACE_RIG_MPM.mpm`, `*_PHYD.phyd`, `*_YWRK_PHYD.phyd`, `*_MISC.misc`. Costume folders under each character hold `.ywrk` files loose. None of those other formats is read yet.

Working copies for Kasumi are in `assets/doax3/` (gitignored), extracted with `psarc.py`.

## TMC models

Koei Tecmo's chunk container, the family of DOA5's models. `tools/re/tmc_dump.py` prints the tree; `tools/re/tmc_mesh.py` reads the geometry (and writes an OBJ with `--obj`).

A chunk: name[8], version u32 (0x01010000), header size u32, chunk size u32, child count u32, then at 0x20 the offset of its offset table (relative to the chunk) and at 0x24 a second table, used by `VtxLay`, `IdxLay` and `LHeader` for sizes. Children at offset 0 are absent. `TMC`'s children, in order: `MdlGeo`, `TTGM`, `VtxLay`, `IdxLay`, `MtrCol`, `MdlInfo`, `HieLay`, `LHeader`, `NodeLay`, `GlblMtx`, `BnOfsMtx`, `cpf`, `RENPACK` (Kasumi's face, 14 of 18 slots used). The TMC's header has the model's name at 0x50 (`KAS_face_00`) and floats after it, probably bounds.

- `LHeader` describes the `TMCL` beside it, which is raw data: kinds at +0x70 (0xC0000002 textures, 0xC0000003 vertices, 0xC0000004 indices), offsets in the first table and sizes in the second. The TMCL starts with u32 3 and its own size.
- `VtxLay`, `IdxLay`: buffers inside the vertex and index blocks, offsets in the first table and sizes in the second.
- `MdlGeo` holds one `ObjGeo` per object. An `ObjGeo` has its sub-meshes in its table (from +0x70) and a `GeoDecl` chunk inside; a name such as `WGT_face` sits at +0x60.
- `GeoDecl` (at the `ObjGeo`'s +0x28): one entry per declaration. Entry +4 is the offset of its element list **from the entry** (with a single entry, at 0x40, that lands on the GeoDecl's 0x80, which is how it was first misread as +0 from the GeoDecl), +0x10 the index count, +0x14 the vertex count. The element list: vertex buffer u32, stride u32, element count u32, then from +0x18 elements of 8 bytes in D3D9's layout: stream u16, offset u16, type u8, method u8, usage u8, usage index u8. Types seen: 2 three floats, 3 four floats, 5 four bytes, 0xA two half floats, 0xB four half floats. Usages: 0 position, 1 weights, 2 bone indices, 3 normal, 5 texture coordinates, 6 tangent.
- **Buffers**: the k-th declaration in file order (over all objects) uses vertex buffer k and index buffer k, and its element list names buffer k too. Checked on 13 of Kasumi's models: every buffer holds exactly its declaration's vertex count times its stride. Indices stay below the vertex count.
- Indices are u16 triangle lists. Positions are in metres.
- Kasumi's face, object 0: stride 128, positions float4 (w 1), normals float4, three float4 weight sets with three byte-index sets (12 bones a vertex), a tangent and two UV sets as four half floats each (the first two are the UV). Other objects use stride 52 to 80 with float3 positions, half-float normals and weights, and the UV as two half floats (type 0xA).
- **Objects** (`ObjGeo` +0x60): `WGT_body`, `WGT_mizugi` (the suit), `WGT_face`, `WGT_hair` are the visible model. `WGT_zdmodel` (hair) and `*T_SHADOW_MODEL` (face) have no normals, probably depth and shadow passes. `WGT_body_zbreak` and `WGT_mizugi_z` repeat the body and suit in the same place; their purpose is not read. `WGT_faceparts` (eyes, mouth) and `*_sweat_*` are modelled around their own node (Kasumi's face parts at Y 0.04 to 0.07), so they need the node bindings. `doax3::drawn_at_rest` keeps the first group only, a choice from names and bounds.
- Some models lie loose beside the archives instead of in them: Nyotengu's, Hitomi's and Momiji's faces and the Aesthetician's head. `doax3::Archives` reads a loose file before an archive's.
- **Space**: costumes and the face share one space, the hips near the origin (a body runs from Y -0.93 to 0.48 and the face from 0.51 to 0.72). Hairstyles are modelled around their first node, `MOT01_Head` (one runs from Y -0.39 to 0.18), so they go on the body's head node.
- `NodeLay`: one `NodeObj` chunk per node: +0x34 0xFFFFFFFF on those read, +0x38 the node's number, name at +0x50 (`MOT01_Head`, `OPT_acs_fronthair...`). A costume has 162 nodes (`MOT00_Hips` first), the face 52, a hairstyle up to 203 (its physics bones, probably). `HieLay` entries are 0x90 bytes: the local matrix (16 floats, column-major, translation in 12 to 14), the parent u32 at +0x40 (0xFFFFFFFF for the root), then a count, the depth and the children's numbers (read loosely). `GlblMtx`: the global rest matrix per node; `BnOfsMtx`: its inverse (checked on the head: +0.504 and -0.504; with rotation on the feet, not checked).
- **Placing objects** (2026-11-18): every object has a node named after it (`WGT_face`, `WGT_faceparts`, `WGT_hair`; names over 15 characters are cut from the front and start with `*`: `*_sweat_cheek_l` is `WGT_sweat_cheek_l`), and the object's vertices go by that node's rest place (`GlblMtx`). Kasumi's `WGT_face` is at Y -0.046, which brings her face's chin (0.507 in the file) under her lip nodes (0.50); `WGT_faceparts` sits on her head (0.504), which puts the eyes (0.04 to 0.07 in the file) at her eye nodes (0.56) and the teeth at the lips; hairstyles' `WGT_hair` is their head (the origin); costumes' objects are at the identity. Honoka's face, modelled around the head, has its node on the head; Marie Rose's `WGT_face` is at -0.088. Checked against each file's own face nodes and by eye, not against the game. `doax3::place_on` puts a part's `MOT01_Head` on the body's and each object on its node; the earlier rule from bounds (centre nearer the origin than the head: on the head) is kept only for objects without a node. `ObjInfo` +0x3C names a face node (41, `OPT_Face_r_nose_a`, on Kasumi's face), not the object's; what it is for is not read.
- **Drawn objects**: those whose declaration has normals (`WGT_zdmodel`, the shadow models and Nyotengu's `WGT_face1`, a copy of her face with neither normals nor coordinates, are left out: depth or shadow passes, probably), not named shadow (any case: Marie Rose's is `WGT_ShadowModel`), `zbreak` or `_z`, and not sweat. Eyes, lashes and teeth (`WGT_faceparts`, Marie Rose's `WGT_leye` and `WGT_toothup`, or the face's second declaration on Helena, Honoka and Nyotengu) are drawn.
- **Lashes**: their sub-meshes list one texture entry, the colour, black with coverage in alpha. The viewer keeps alpha (alpha test) for materials on hair objects and for sub-meshes with a single entry, unless an opaque material shares the texture (the face's atlas, which the eyeballs use). Kind 3 textures on the eyeballs are near black and opaque (Kasumi's 8 and 10), not the iris, which is in the face's atlas.
- In the viewer (2026-11-17): every costume, the face and the chosen hairstyle, lifted so the body's lowest point is on the ground. Helena's first hairstyle has a strand standing straight up from the head, probably a physics chain in its rest pose, not looked into. Since 2026-11-18 with colour textures (first kind-0 entry per sub-mesh); hair is alpha tested, not blended. Faces, eyes and fringes sit right by eye on all nine characters since objects go on their nodes (2026-11-18). Costume 0 is the same for everyone (`AYA_bi_02_a`, first by name), as every outfit exists for every body.
- **Textures** (read 2026-11-18, `doax3::texture_files`, `decode_texture`; `tools/re/gnf.py` lists them). `TTGM` has no child table: `TTGH` follows its header and `TTGL` is at TTGM + its +0x28. `TTGL`: count at +0x14, offsets (+0x20) and sizes (+0x24) tables, offsets from the TMCL's texture block (LHeader kind 0xC0000002). Each is a GNF: "GNF ", header size after 8 bytes (0x28), version 2, one texture, file size, then the 32-byte T# (GCN `SQ_IMG_RSRC_WORD0..7`: format in WORD1 bits 20-25, number format 26-29, width-1 and height-1 in WORD2, tile mode WORD3 bits 20-24, type 28-31, pitch-1 WORD4 bits 13-26); data right after the 0x30 header, level 0 first, each level padded to whole 8x8-element tiles. Over all 2224 models of the game: 26016 BC7 2D textures, 2175 of type 10 (one level, twice a 2D level's data, probably a 3D texture of depth 2; not read), 21 RGBA8 and 1 BC1, **all in tile mode 13** (`Thin_1dThin`): micro tiles of 8x8 elements (4x4 blocks for BC) in rows over the pitch, Morton order inside (x0 y0 x1 y1 x2 y2). Checked by eye on BC7 (face, normal map, lashes, hair, suits); RGBA8 and BC1 decode the same way, not looked at.
- **Sub-meshes** (the `ObjGeo`'s children): +4 the `MtrCol` entry, +0x10 the texture entry count and from +0x14 their offsets from the sub-mesh, **+0x3C the declaration within the object** (hair objects interleave two), +0x80 first index, index count, first vertex, vertex count (indices are absolute in the declaration's buffer). Texture entry: slot, kind, texture. Kind 0 is colour; a second kind-0 entry on the face and body is a detail layer (veins, `KAS_FACE` texture 7, mostly transparent); kinds 1 and 2 are maps (pink and blue, normals probably; kind 1 is the type 10 texture on the face); kind 3 a second colour on the eyes. `MtrCol` entries: 0x60 bytes of colours, then at +0xD0 the entry's number, +0xD8 a small value, +0xDC how many sub-meshes use it; no blend flag found.
- **Alpha**: the skin's colour textures carry a mask (Kasumi's face mean 0.22, body 0.33, on opaque surfaces), suits read are opaque, hair's alpha is the strands' coverage. The viewer keeps alpha on textures hair objects use (alpha test at 0.1) and makes the others opaque: a stand-in by name (`doax3::alpha_is_coverage`).

## Motions (MPM)

Read 2026-11-18 from the files and from the game's code. `eboot.bin` is a fake-signed SELF whose segments are neither encrypted nor compressed: the code segment (SELF offset 0x4110, 0x701E20 bytes, loaded at 0) and the data segments can be laid out by their program headers and disassembled as x86-64 (`objdump -b binary -m i386:x86-64`). The curve stepper is at 0x5702A0; the code at 0x57019D checks a curve's 00 07 header. Found from the scale constant 1/16384 (0x38800000 at 0x697C9C).

- File: `char_dat` holding a `char_dat` at 0x40 with six children (offsets in its table at +0x30). Child 0: u64 offsets to the motions, relative to child 0, ended by 0. Child 3: a flag word (0x10000 or 1), the motion count, the bone count, then the first bone's name (`MOT00_Hips` in `*_INGAME_MPM`, 21 bones; `OPT_Face_Root` in face files, 44 bones). Children 4 (a hierarchy of 0x10-byte entries) and 5 (a `g` chunk) are not read.
- A motion: `bones * 9` u64 offsets to curves (relative to child 0), then 0. Per bone: position x, y, z (metres, local to the parent), rotation x, y, z (radians, 0 to 2π, absolute local angles: the thighs' and shoulders' rest tilts of ±15° are in them), scale x, y, z. Body bone n is node `MOTnn_*` (`MOT06_LeftUpLeg` sits at (0.077, -0.035, -0.022) in both the motion and the model). The hips' position is in the world (Y 0.879 for Kasumi).
- A curve: 00 07, then commands of a 16-bit count (bytes 0, 1) and a code (byte 2), stepped one value a frame into an integer accumulator scaled by 1/16384: 0x80 last value (24 bits, bytes 0, 1, 3), 0x7A last value (32 bits), 0x7F and 0x7E runs of 8- and 16-bit deltas read a frame at a time, 0x7D and 0x7C one delta repeated over the run, 0x7B a 32-bit value, anything else a 24-bit value (bytes 0 to 2). Delta codes are not taken on the first frame while the accumulator is 0. In all 51 of Kasumi's in-game motions every channel decodes to the same frame count (20 to 2410). `tools/re/doax3_mpm.py` and `src/formats/doax3_motion.rs` decode them.
- Skinning: weights (usage 1, three sets of four half floats) and node indices (usage 2, three sets of four bytes) go through the palette in the object's `NodeObj` (+0x60: offset of a block whose +4 is the count and whose +0x60 starts u32 node numbers). Checked: the heaviest node lies 3 to 6 cm from its vertices (median) on Kasumi's body, suit and hair. Vertices are posed by `posed * GlblMtx⁻¹` of each node, after the object is placed on its node.
- Not read: the SKTM (a table of 0x1B and 0x37 entries of offsets and small counts, with -1 padded lists of pairs: a state machine or a motion set, not a skeleton), which motion is which, the face motions' bone order, the motion sets of the scenes (`conte/CNT_*`: `BODY_S`, `BODY_L`, `BODY_SS` by body size, `HAND_*`, `FACE_*`).
